# Age-Restricted (NSFW) Channels

- **Status**: implemented 2026-09-22 (migration not applied, manual test plan not run)
- **Date**: 2026-09-18
- **Related**: [`member-timeout-and-slowmode.md`](member-timeout-and-slowmode.md)

## Goal

Let a channel be flagged as age-restricted so a member must confirm they are 18+ once before they can read or post in it. Today `Channel` has no such flag (`apps/api/prisma/models/channels.prisma:21-53`) and `User` has no birthdate or age-confirmation field (`apps/api/prisma/models/users.prisma:31-79`, read in full — confirmed absent) — there is no age gate of any kind. The only existing NSFW-adjacent concept is a message report reason literal (`packages/shared/src/api-contract.ts:564`), unrelated to gating content.

This is a **self-attested checkbox, not real age verification**. It stops a channel's content from appearing by default and gives moderators/legal a documented "user confirmed" record; it does not verify identity or age and must never be described to users or in any UI copy as doing so.

**Acceptance criteria**:

- [ ] `Channel.isAgeRestricted` can be set on create/update by anyone with `ManageChannels`, same as every other channel setting.
- [ ] A member who has never confirmed gets `403` from every message-content endpoint of an age-restricted channel (list, search, pins, send, edit, delete, react, pin/unpin, threads, forum posts) — confirmed once, they stay confirmed everywhere (no per-channel reconfirmation).
- [ ] The channel itself (name, topic, existence in the sidebar) stays visible and un-gated; only message content is blocked — matching "viewing the channel row shows a gate screen when opened", not "the channel disappears".
- [ ] A push notification for a message in an age-restricted channel never includes the author or message content in its body, regardless of the recipient's confirmation state.
- [ ] `POST /users/me/age-confirmation` records the confirmation once, is idempotent, and the resulting timestamp comes back on `GET /users/me`.

## Scope

**In scope**

- `Channel.isAgeRestricted Boolean` column + DTO/service wiring (create, update, audit log).
- `User.ageConfirmedAt DateTime?` column + a confirmation endpoint.
- A single server-side enforcement point for all message-content endpoints of an age-restricted channel.
- Gating realtime socket room membership for message-content events: an unconfirmed member's socket must not join, and must not receive events from, an age-restricted channel's room; a channel flipped to age-restricted evicts its unconfirmed members' sockets from the room (**decided 2026-09-21**, see Changes and Decided).
- Push notification body suppression for age-restricted channels.
- Web: a settings toggle (`ChannelSettings.tsx`), a gate screen in place of the message list (mirroring `RulesGate.tsx`), and a badge on the channel row.
- i18n keys in `channels.ts` (en/vi).

**Out of scope**

- Real age/identity verification (document upload, third-party KYC) — flagged as a legal limitation below, not solved here.
- Per-channel confirmation / re-confirmation — one global `ageConfirmedAt` covers every age-restricted channel on every server (**decided 2026-09-21**, see Trade-offs and Decided).
- Gating rules-screening's own equivalent realtime gap: `requireOnboardingAccepted` is still never consulted by `RealtimeAccessService.listViewableChannelIds` (`apps/api/src/modules/realtime/realtime-access.service.ts:76-85`) or by `MessagesGateway.joinChannel`. That gap is **not** being closed by this doc — only the age-restriction gate gets a socket-side check; onboarding's realtime gap stays exactly as it is today, out of scope here.
- Gating link previews (`apps/api/src/modules/link-previews/link-previews.service.ts`) — a link preview fetches metadata for a pasted URL regardless of which channel posted it; it carries no channel/age context today and adding one is a bigger change than this doc's budget.
- Gating server discovery (`apps/api/src/modules/servers/server-discovery.service.ts`) — `DiscoveryServerCard` (`packages/shared/src/server-discovery.ts:17`) exposes server-level `name`/`description`/`tags`/`memberCount` only, no channel list or channel content; there is nothing channel-scoped to leak there.
- Webhook-posted messages (`apps/api/src/modules/webhooks/webhook-execute.controller.ts`) — a webhook can only be created on a channel a `ManageChannels` holder already set up (`webhooks.service.ts:44`), so an age-restricted channel accepting webhook posts is the same trust boundary as accepting human posts; no separate gate needed.
- Bots exempt from the age gate entirely (**decided 2026-09-21**, see Edge cases and Decided) — matches the onboarding precedent (`member.kind === 'BOT'`, `onboarding-gate.ts:25`), so there is no "bot has no UI to click confirm" problem to solve.
- A minimum-age input / birthdate collection at signup — `ageConfirmedAt` is a boolean-in-time ("this user has clicked confirm"), not a computed age.

## Current behavior

- `Channel` model (`apps/api/prisma/models/channels.prisma:21-53`): no age/NSFW field. `slowmodeSeconds`, `isPrivate`, `postGuidelines` sit beside where `isAgeRestricted` will go.
- `ChannelsService.createChannel`/`updateChannel` (`apps/api/src/modules/channels/channels.service.ts:19-42`, `:70-102`) both require `Permission.ManageChannels`, normalize `dto.name`, and write an audit log (`CHANNEL_CREATE`/`CHANNEL_UPDATE`) — the pattern every new channel field (`slowmodeSeconds`, `postGuidelines`) already follows.
- `ChannelsService.requireReadableChannel` (`apps/api/src/modules/channels/channels.service.ts:164-171`) is the **single choke point** for message content: it is called first by `MessagesService.listMessages` (`messages.service.ts:61`, which also carries the search filters, `messages.search.ts` — search is always scoped to one `channelId` route param, `messages.controller.ts:32-46`, so there is no separate cross-channel search leak), `markChannelRead` (`:121`), `listPinnedMessages` (`:148`), `requireCanPostInChannel` (`:173`), `updateMessage` (`:404`), `deleteMessage` (`:446`), `toggleReaction` (`:481`), `togglePin` (`:515`), `findMessageForUser` (`:558`), and `requireThreadRoot` (`:640`, used by thread listing/replies). `requireReadableForumChannel` (`:177-181`) wraps it for forum posts.
- `ChannelsService.getChannel`/`listChannels` (`:44-67`) only check `Permission.ViewChannel`, not `requireReadableChannel` — this is how the channel row itself (name, topic, sidebar listing) stays visible independent of message-content gating.
- `PermissionsService.requireOnboardingAccepted` (`apps/api/src/modules/permissions/permissions.service.ts:79-92`) is today's closest precedent for a "confirm once, gate participation everywhere" flag: `ServerMember.onboardingAcceptedAt` (`apps/api/prisma/models/servers.prisma:126`), checked by `memberNeedsOnboarding` (`apps/api/src/modules/permissions/onboarding-gate.ts:18-31`) and called from every send/react/vote/join path (`messages.service.ts:194,310,409,483`, `polls.service.ts:161`, `soundboard-playback.service.ts:45`, `realtime-access.service.ts:98`) — but it does **not** gate reads (`listMessages` never calls it) and it does **not** gate socket room joins, both cited above as the same shape of gap this feature inherits if left unaddressed for reads/realtime respectively. Age-restriction differs from onboarding in one respect this doc follows deliberately: it gates reads too, because the point is to keep the content itself from displaying, not just to stop new posts.
- `PushService.sendMentionPush` (`apps/api/src/modules/push/push.service.ts:69-98`) builds a payload with `body: this.i18n.t(locale, 'push.channelMessage.body', { author, content: truncate(input.content, 100) })` (`:87-90`) — the message content and author always appear in the push body today, regardless of mute state or any gate.
- `MessagesService.notifyMentionedUsers` (`apps/api/src/modules/messages/messages.service.ts:703-740`) already has the `channel`/`channelId` in scope at its only call site, `createMessage` (`:210`, `channel` returned from `requireCanPostInChannel`), and checks `Permission.ViewChannel` (`:725-729`) before calling `sendMentionPush` — it does not know about age-restriction today because the field does not exist yet.
- `User` model (`apps/api/prisma/models/users.prisma:31-79`, read in full): no birthdate, no age-confirmation field. `emailVerifiedAt DateTime?` (`:44`) is the closest existing "confirmed once" pattern on `User` itself, as opposed to on `ServerMember`.
- Web gate precedent: `RulesGate.tsx` (`apps/web/src/components/onboarding/RulesGate.tsx`) is rendered **in place of the whole `ChatPanel`** when `server.needsOnboarding` is true (`AuthenticatedWorkspace.tsx:62-64`), because onboarding is server-scoped. Age-restriction is channel-scoped, so the gate must instead render inside the per-channel view, not swap out the whole panel — there is no existing channel-scoped equivalent to copy exactly; `RulesGate.tsx` is the closest structural and visual reference (loading/error/confirm states, `Banner`/`Button`/`Checkbox` from `@/components/ui`).
- `ChannelSettings.tsx` (`apps/web/src/components/settings/ChannelSettings.tsx:176-181`) already renders an `isPrivate` `SwitchRow`; the slowmode `<select>` (`:33-47`) is the pattern for a channel-level enum/boolean setting reaching `updateChannelSettings`.
- `User` shared contract (`packages/shared/src/api-contract.ts:22-37`): no `ageConfirmedAt`; `emailVerifiedAt?: Date | null` (`:34`) is the closest sibling field shape to copy.
- Latest migration: `apps/api/prisma/migrations/20260918007000_add_stage_channels`.
- Error-message-to-code mapping (`apps/api/src/common/i18n/error-codes.ts:1-2`) is generated by `npm run i18n:check`; a new exception message needs no manual entry there, only to exist as a literal the scanner can find (see `RULES_NOT_ACCEPTED_MESSAGE`, `apps/api/src/modules/permissions/onboarding-gate.ts:4`, for the constant-literal pattern).
- Socket room membership: `RealtimeGateway.handleConnection` joins a human socket only to `userRoom(userId)` and its DM conversation rooms at connect time (`apps/api/src/modules/realtime/realtime.gateway.ts:83-96,143-150`); it never preloads channel rooms. A channel room is joined on demand by `MessagesGateway.joinChannel`'s `channel:join` handler (`apps/api/src/modules/realtime/messages.gateway.ts:38-46`), which calls `RealtimeAccessService.requireViewableChannel` (`realtime-access.service.ts:19-30`, today only checks `Permission.ViewChannel`) before `client.join(this.publisher.channelRoom(...))`. `requireViewableChannel` has exactly one call site (`grep` confirmed), so it is a second, socket-side choke point next to `ChannelsService.requireReadableChannel`. The web client emits `channel:join` every time the active channel changes (`apps/web/src/hooks/useChannelOpening.ts:120-134,137-139`), not once at login — there is no `channel:leave`, so a joined room is kept for the rest of the socket's life (`grep` for `channel:leave` across `apps/api/src`/`apps/web/src`: no results). A bot socket instead joins every channel it can view up front, at connect (`connectBot`, `realtime.gateway.ts:122-140`, via `listViewableChannelIds`).
- The existing mechanism to move an already-connected socket in or out of a room without a reconnect is `RealtimePublisher.joinUsersToRoom`/`removeUsersFromRooms` (`apps/api/src/modules/realtime/realtime-publisher.service.ts:35-44`, `server.in(userRoom(...)).socketsJoin/socketsLeave(room)`). `ServerModerationService.announceRemoval` already uses `removeUsersFromRooms` to evict a kicked/banned member's socket from a server's channel rooms (`apps/api/src/modules/servers/server-moderation.service.ts:211-228`), the direct precedent this doc reuses for evicting unconfirmed members on an age-restriction flip. There is no existing precedent for _adding_ a user to a channel room outside of the on-demand `channel:join` flow — `joinUsersToRoom`'s only current caller is the group-DM join path (comment at `realtime-publisher.service.ts:35`), not a channel room.

## Changes

### Rules / Flow

1. `Channel` gains `isAgeRestricted Boolean @default(false)`, settable via `CreateChannelDto`/`UpdateChannelDto` by anyone with `ManageChannels` — same authorization as every other channel field, no new permission.
2. `User` gains `ageConfirmedAt DateTime?`, `null` meaning "never confirmed". It is **global**, not per-channel and not per-server: once set, it satisfies the gate for every age-restricted channel on every server the user can already view. Chosen over a per-channel/per-server row (see Trade-offs).
3. A new pure helper `channelNeedsAgeConfirmation(channel: { isAgeRestricted: boolean }, user: { ageConfirmedAt: Date | null }): boolean` returns `channel.isAgeRestricted && !user.ageConfirmedAt`, mirroring the shape of `memberNeedsOnboarding` (`onboarding-gate.ts:18`).
4. `PermissionsService` gains `requireAgeConfirmed(userId: string, channelId: string)`, mirroring `requireOnboardingAccepted`'s shape: loads the channel's `isAgeRestricted` and the caller's `ageConfirmedAt`, throws `ForbiddenException(AGE_CONFIRMATION_REQUIRED_MESSAGE)` when `channelNeedsAgeConfirmation` is true.
5. `ChannelsService.requireReadableChannel` calls `this.permissions.requireAgeConfirmed(userId, channel.id)` right after the existing `requireChannelPermission(ViewChannel)` check (`channels.service.ts:169`). Because every message-content path in Current Behavior funnels through this one method (directly or via `requireReadableForumChannel`), this single addition gates listing, searching, pins, sending, editing, deleting, reacting, pin/unpin, thread listing and replies, and forum posts, all at once — the same "one choke point, no drift" property `requireCanPostInChannel` already relies on for send-side gates (`messages.service.ts:170-172` comment).
6. `ChannelsService.getChannel`/`listChannels` are **not** changed — the channel row (name, topic, `isAgeRestricted` flag itself) stays visible so the client can render a locked/18+ badge and let the user click in; the gate only blocks what is inside.
7. `POST /users/me/age-confirmation` (new, `UsersController`/`UsersService`): sets `ageConfirmedAt = now()` if currently `null`; a repeat call is a no-op that returns the original timestamp (idempotent, matching the repo's "duplicate PATCH" idiom in `timed-notification-mute.md`'s edge cases). No unconfirm endpoint — there is no product requirement to revoke a self-attestation, and Discord's own equivalent has none either (inferred from product intent stated in the task, not read from a spec).
8. `MessagesService.notifyMentionedUsers` gains `isAgeRestricted: boolean` on its input (passed from `createMessage`'s already-loaded `channel.isAgeRestricted`, `messages.service.ts:210`) and forwards it to `PushService.sendMentionPush`.
9. `PushService.sendMentionPush` branches on `input.isAgeRestricted`: when true, the body is the i18n key `push.channelMessage.ageRestrictedBody` (a generic "New message in an age-restricted channel", no author, no content) instead of `push.channelMessage.body`; the title stays `push.channelMessage.title` (channel name only, already generic). This applies **regardless of the recipient's own `ageConfirmedAt`**, unconditionally (**decided 2026-09-21**, see Decided) — a lock-screen preview is a different, more public exposure surface than an in-app read, and Discord's own push previews behave the same way (inferred from product intent, not read from a spec).
10. Web: `ChannelSettings.tsx` gets an `isAgeRestricted` `SwitchRow`, styled and placed next to the existing `isPrivate` one (`:176-181`). Channel rows in the sidebar show a small "18+" badge when `channel.isAgeRestricted` is true (purely informational, not a lock — the lock is the gate screen). The active channel's message view renders a new `AgeGate` component (new file, modeled on `RulesGate.tsx`'s loading/error/confirm states, reusing `Banner`/`Button`/`Checkbox`) instead of the message list/composer whenever `channelNeedsAgeConfirmation(activeChannel, auth.user)` is true on the client (same pure check, ported to TS) — the API is still the real gate; this is the same "convenience, not the gate itself" framing `RulesGate.tsx`'s own comment uses (`RulesGate.tsx:14-17`). Confirming calls `POST /users/me/age-confirmation` and updates the cached `auth.user.ageConfirmedAt` (same `setAuth` pattern already used elsewhere for updating the cached user after a mutation — inferred from the existing `AuthState`/`setAuth` shape in `apps/web/src/api.ts:12-24`, not traced through every call site).

**Realtime gating (decided 2026-09-21 — see Decided; this used to be out of scope)**

11. `RealtimeAccessService.requireViewableChannel` (`realtime-access.service.ts:19-30`) gains a call to `this.permissions.requireAgeConfirmed(userId, channel.id)` right after its existing `Permission.ViewChannel` check — the same method Rule item 4 defines, so the socket join gate and the REST gate share one authorization function instead of drifting apart. This method's only call site is `MessagesGateway.joinChannel`'s `channel:join` handler (`messages.gateway.ts:38-46`): an unconfirmed member's `channel:join` for an age-restricted channel now throws before `client.join(this.publisher.channelRoom(...))` runs, so the socket never joins the room and can never receive `message:created`/`reaction:updated`/`typing:*` for it. This satisfies "must not join, and must not receive events from, an age-restricted channel's room."
12. `PermissionsService.requireAgeConfirmed` (Rule item 4) loads the caller's `ServerMember.kind` for the channel's server alongside `Channel.isAgeRestricted`/`User.ageConfirmedAt`, and returns without throwing when `kind === 'BOT'` — mirroring `memberNeedsOnboarding`'s exemption (`onboarding-gate.ts:25`). Because both the REST choke point (item 5) and the socket choke point (item 11) call this one method, a bot is exempt from the age gate everywhere at once, with no separate code path to keep in sync (**decided 2026-09-21**).
13. `ChannelsService.updateChannel` (`channels.service.ts:69-104`), when the update sets `isAgeRestricted: true` on a channel that was not already restricted (`dto.isAgeRestricted === true && !existing.isAgeRestricted`), looks up the server's non-bot members who have not confirmed (`prisma.serverMember.findMany({ where: { serverId: existing.serverId, kind: { not: 'BOT' }, user: { ageConfirmedAt: null } }, select: { userId: true } })`) and calls `RealtimePublisher.removeUsersFromRooms(unconfirmedUserIds, [this.realtime.channelRoom(channelId)])` — the exact method `ServerModerationService.announceRemoval` already uses to evict a kicked/banned member's socket from a room (`server-moderation.service.ts:222-228`). This satisfies "when a channel is flipped to age-restricted, unconfirmed members' sockets leave the room." `ChannelsModule` gains `RealtimePublisherModule` as an import to reach `RealtimePublisher`, the same standalone-module pattern `ServersModule` already uses to reach it without a cycle back into `RealtimeModule` (`servers.module.ts:5-6`, established by commit `aedfde5`).
14. Regaining the room after confirming needs no new push mechanism: a socket only ever joins a channel's room on demand, when a client opens that channel (`useChannelOpening.ts:120-134` emits `channel:join` on every `channel?.id` change) — there is no existing or needed mechanism that pre-joins a user to every channel room it can view, so there is nothing to "grant" for channels not currently open. The one gap is the currently-open channel itself: `useChannelOpening`'s effect only re-runs on `channel?.id`/`auth?.accessToken`/`socket` changing (`useChannelOpening.ts:137-139`), none of which change when only `ageConfirmedAt` updates, so it does not re-emit `channel:join` on its own. **Minimal addition**: `AgeGate`'s confirm handler re-emits `channel:join` for the active channel (the same event `useChannelOpening` already sends when a channel is first opened) right after `POST /users/me/age-confirmation` resolves — the existing on-demand join call, invoked one extra time, with no reconnect.

Reason: a bot has no UI to click "confirm" and, like onboarding, the admin who authorized it into the server already chose its access.                                                                                            |

| Confirmed member reopens a channel they already had open before confirming                                                                                | `AgeGate`'s confirm handler re-emits `channel:join` (Rule item 14); the message list and live updates resume without a reconnect.                                                                                                                                                                                                                                                                                                                              |

**API contract**

- `POST /channels` / `PATCH /channels/:channelId` (existing endpoints) — request body gains `isAgeRestricted?: boolean`; response `channel` includes it. No new status codes; unchanged `403` (`ManageChannels`), `404` (channel/category not found).
- `GET /channels/:channelId/messages`, `POST /channels/:channelId/messages`, `PATCH /messages/:id`, `DELETE /messages/:id`, `POST /messages/:id/reactions`, `POST /messages/:id/pin`, thread and forum-post endpoints — all unchanged shapes, but now additionally answer `403 You must confirm your age to view this channel` when the channel is age-restricted and the caller has not confirmed.
- `POST /users/me/age-confirmation` (new)
  - Request: none.
  - Response `200`: `{ user: User }` (with `ageConfirmedAt` set).
  - Errors: `401` unauthenticated (existing guard only; no other failure mode — setting your own confirmation cannot conflict or be invalid).
- Socket event `channel:join` (existing, `messages.gateway.ts:38-46`) — unchanged request/ack shape, but now additionally throws the age-confirmation error before joining the room when the channel is age-restricted and the caller has not confirmed (Rule item 11); no new socket event is added for eviction — it is a silent `removeUsersFromRooms` call (Rule item 13), the same as the existing kick/ban eviction, with no ack to the affected client.

**DB / migration**

- Table `Channel`: `ADD COLUMN "isAgeRestricted" BOOLEAN NOT NULL DEFAULT false` — safe, defaulted, no backfill needed (every existing channel is unrestricted, matching today's implicit behavior).
- Table `User`: `ADD COLUMN "ageConfirmedAt" TIMESTAMP(3)` — nullable, no default, no backfill (every existing user is unconfirmed and will hit the gate the first time they open an age-restricted channel, which is correct: they never confirmed).
- Migration `apps/api/prisma/migrations/20260922001000_add_age_restricted_channels/migration.sql`, hand-written, both `ALTER TABLE ... ADD COLUMN` statements with a `down()` dropping both columns. Both are nullable-or-defaulted additions on tables with no unusual size assumption stated in this repo's other channel/user migrations — metadata-only on Postgres, no lock-duration concern.
- No new index: `isAgeRestricted` and `ageConfirmedAt` are only ever read by primary-key lookup (the channel/user already loaded by `requireReadableChannel`/`requireAgeConfirmed`), never filtered in a `WHERE` across many rows.

**Libraries** — none new; reuses `class-validator`'s `@IsBoolean()` and the existing `Banner`/`Button`/`Checkbox`/`SwitchRow` UI primitives.

## Trade-offs

| Option                                                                                                           | Pros                                                                                                                                                                                                                                                                                                                                                                                      | Cons                                                                                                                                                                                                                                                                                                                     | Verdict                                                                                                                                                                           |
| ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A (chosen): `User.ageConfirmedAt`, global**                                                                    | One confirmation for the whole platform, matching the plain-language feature ask ("the confirmation is remembered"); one column, one read per gate check; consistent with `emailVerifiedAt`'s existing "confirmed once on the user" shape.                                                                                                                                                | Cannot express "this server has stricter rules than that one" — a moderator cannot force a fresh confirmation for their own age-restricted channel.                                                                                                                                                                      | Chosen — no requirement asks for per-scope confirmation, and it is strictly simpler to reason about, audit, and implement.                                                        |
| B: per-channel confirmation row (e.g. `ChannelAgeConfirmation { userId, channelId }`)                            | A server/channel could require its own explicit confirmation; more auditable per-channel.                                                                                                                                                                                                                                                                                                 | A new table + N rows per active user, one lookup per channel instead of per user; nothing in the ask calls for scoping it this finely; closer to over-engineering the "remembered" requirement.                                                                                                                          | Rejected — cost without a stated benefit.                                                                                                                                         |
| C: gate only writes (mirror `requireOnboardingAccepted`'s placement), leave reads open                           | Smaller diff, reuses the exact onboarding pattern verbatim.                                                                                                                                                                                                                                                                                                                               | Directly contradicts the stated goal ("viewing such a channel shows a gate screen") — the content itself must not display, not just be un-repliable.                                                                                                                                                                     | Rejected — does not meet the acceptance criteria.                                                                                                                                 |
| D: client-only gate, no server enforcement                                                                       | Trivial to build, no migration.                                                                                                                                                                                                                                                                                                                                                           | Violates this repo's own rule ("hiding a button in the UI is not authorization", `~/.claude/rules/security.md`) — any authenticated user could call the message endpoints directly and read age-restricted content with zero confirmation.                                                                               | Rejected outright.                                                                                                                                                                |
| **E (chosen): suppress push body content for age-restricted channels unconditionally**                           | Removes the lock-screen leak entirely, independent of any client-side confirmation state that a notification service cannot know at delivery time anyway (push is fire-and-forget from the server).                                                                                                                                                                                       | Slightly less useful push previews for genuinely age-restricted-but-benign channels (e.g. a channel restricted for legal caution rather than graphic content).                                                                                                                                                           | Chosen — a lock screen is public by default; the cost is a marginally less informative notification, not a leak.                                                                  |
| F: only suppress push body when the recipient has not confirmed                                                  | Keeps rich previews for confirmed users.                                                                                                                                                                                                                                                                                                                                                  | Requires loading the recipient's `ageConfirmedAt` on every mention push (`sendMentionPush` currently has no such lookup) and still leaks content to anyone who can see the confirmed user's lock screen — the confirmation is about _that user's_ willingness to view it in-app, not about who else can see their phone. | Rejected — the safer, simpler default.                                                                                                                                            |
| **G (chosen): gate the socket `channel:join` room-join, evict on flip**                                          | Reuses `requireAgeConfirmed` (already built for REST) at the one socket call site that joins a channel room, and reuses `RealtimePublisher.removeUsersFromRooms` (already built for kick/ban) for the flip case — no new authorization primitive, no new eviction primitive. A member who never joins the room can never receive an event from it, so per-event filtering is unnecessary. | A channel flip needs one extra `serverMember` query (unconfirmed members of the server) before the eviction call; the already-open, already-stale message view has no live "this channel changed" push to refresh it (pre-existing gap, see Risks).                                                                      | Chosen — smallest change that actually closes the leak, reusing two methods this repo already has for the exact same shape of problem (kick/ban).                                 |
| H: check age confirmation on every emit (`message:created`, `reaction:updated`, ...) instead of gating room join | Would also cover a member who somehow stayed in the room despite a flip, without a separate eviction step.                                                                                                                                                                                                                                                                                | Requires loading every room member's confirmation status on every single event emitted to a channel room — a per-message DB fan-out that scales with room size and message volume, on the hottest realtime path in the app; also duplicates the join-time check instead of replacing it.                                 | Rejected — gating join once is strictly cheaper than filtering every event forever, and the eviction call already removes the one case per-event filtering would otherwise catch. |

What the chosen option costs: `requireReadableChannel` now does one extra `ForbiddenException` branch on every message-content call, a query already paid for by the existing `requireChannelPermission` lookup (channel row already loaded) plus one small `User` lookup for `ageConfirmedAt` — negligible. The push change loses per-user push personalization for age-restricted channels, a deliberate trade for not leaking content on a lock screen. Gating the socket join and evicting on flip (Option G) costs one extra `PermissionsService` call on `channel:join` (already resolving the channel and calling `PermissionsService` for `ViewChannel` in the same method) and one extra `serverMember` query on the rare "flip a channel to restricted" write path, not on any hot read/write path.

**Decided** (2026-09-21, four open questions resolved as follows):

- **Realtime socket-room membership IS gated in this change** (reversing the original "out of scope" draft). Reason: the REST gate is meaningless if the content still streams to an unconfirmed member's client over the socket anyway — a UI-only or REST-only gate is not authorization, the same principle `rules/security.md` states for a hidden button. Rules items 11–14, Edge cases, and the Test plan below spell out the mechanism. The onboarding-screening equivalent gap is intentionally **not** touched by this decision and stays exactly as it is today (see Scope, Out of scope).
- **Bots (`ServerMember.kind === 'BOT'`) are exempt from the age gate.** Reason: matches the existing onboarding precedent (`memberNeedsOnboarding`, `onboarding-gate.ts:25`) — a bot has no UI to click "confirm," and the admin who authorized its role into the server already made that access decision.
- **Push notification bodies for age-restricted channels are suppressed unconditionally**, regardless of the recipient's own confirmation state (Rule item 9, Trade-off E). Reason: a lock-screen preview is a more public exposure surface than an in-app read, and checking the recipient's state would need a lookup `sendMentionPush` does not otherwise need for a benefit (richer previews) that does not outweigh the leak risk.
- **One global `User.ageConfirmedAt`, not per-channel/per-server** (Rule item 2, Trade-off A). Reason: no requirement asks for scoping the confirmation more finely, and a single column is simpler to reason about, audit, and query than a join table with no stated use case.

## Risks & rollback

- **What can break**: any client that reads a message-content endpoint on a channel later flagged `isAgeRestricted` will start getting `403` until the user calls the new confirm endpoint — this is the intended behavior, but it is a real, user-visible change for existing members of a channel a moderator restricts after the fact. The same channel's socket room now evicts its already-connected unconfirmed members at that moment (Rule item 13) — their open message view stops receiving live events but is not itself cleared or replaced (see Edge cases), since there is no `channel:updated` socket event today to prompt a refresh.
- **Not covered**: real identity/age verification (the self-attested checkbox is explicitly a legal limitation, not a solution — must be stated in any privacy/ToS-facing copy, not implied as verification); rules-screening's own realtime gap (deliberately left as-is, see Scope); link-preview gating; a live "channel settings changed" push to refresh an already-open channel view (pre-existing gap, not introduced by this doc).
- **Rollback**: revert the code; the migration is additive on both tables (`down()` drops both columns). Rows written with a non-null `ageConfirmedAt` are simply lost on rollback — acceptable, since rolling back also removes the feature that reads it, and no other column depends on it. `Channel.isAgeRestricted` rows revert to `false` semantics implicitly once the column is gone (no orphaned state elsewhere, since no other table references it).

## Test plan

Not covered by automated tests (repo has no test suite by policy).

**Manual**

1. `ManageChannels` holder sets `isAgeRestricted: true` on a text channel via `PATCH /channels/:id` → `GET` the channel shows `isAgeRestricted: true`; the channel still appears in `GET /servers/:id`'s channel list for every member.
2. A member who has never confirmed calls `GET /channels/:id/messages` directly (bypassing the UI) → `403 You must confirm your age to view this channel`.
3. Same member calls `POST /users/me/age-confirmation` → `200`, `user.ageConfirmedAt` is set; retrying `GET /channels/:id/messages` now succeeds; a second `POST /users/me/age-confirmation` returns the same timestamp unchanged.
4. Confirmed member opens an age-restricted channel in a **different** server they are also a member of → no second confirmation prompt (global, not per-channel).
5. Confirmed member sends a message in the age-restricted channel that `@mentions` an unconfirmed member who is offline → the unconfirmed member's push notification shows the generic age-restricted body, not the author or message text; repeat with the recipient confirmed → body is still generic (Rules item 9).
6. In the web app: open the age-restricted channel as an unconfirmed user → `AgeGate` renders instead of the message list; click confirm → the message list and composer render normally without a page reload.
7. Turn `isAgeRestricted` off again → a previously-blocked unconfirmed member can now read without ever confirming.
8. An unconfirmed member's socket emits `channel:join` for the age-restricted channel → the ack is a refusal, not `{ ok: true, ... }`; a second, confirmed member then posts a message in that channel → the unconfirmed client's socket receives no `message:created` event for it (never joined the room).
9. A `ManageChannels` holder flips an existing, previously-unrestricted channel to `isAgeRestricted: true` while an unconfirmed member's socket already has it open (already `channel:join`-ed before the flag was set) → that member's socket stops receiving `message:created`/`reaction:updated`/`typing:*` for the channel immediately after the flip.
10. A bot member (`ServerMember.kind = 'BOT'`) is added to an age-restricted channel with no `ageConfirmedAt` ever set → its REST calls to that channel's message-content endpoints succeed, and its gateway socket's room membership for that channel is unaffected by the age gate.

## Deviations

Built 2026-09-22 against the approved spec. Differences from the text above:

1. **Migration name**: `20260922001000_add_age_restricted_channels` (the spec was written before `20260921001000`–`20260921003000` landed). The SQL matches `prisma migrate diff` from the previous schema exactly. Not applied to any database.
2. **Rule 14 mechanism**: `AgeGate` does not emit `channel:join` itself. `AppShell.tsx` computes `isAgeGated` with `channelNeedsAgeConfirmation(channel, auth.user)` and passes it to `useChannelOpening`, which skips the message/pin fetch and the `channel:join` while it is true and re-runs when it flips to false. Confirming therefore loads the message list and joins the room in one step, without a reconnect. The spec's version (re-emit only) would have joined the room but left the list empty, and Test plan step 6 needs the list. It also keeps the gated channel from filling the chat panel with `403` banners.
3. **Session responses carry `ageConfirmedAt`**: `AuthService.getMe` (every sign-in path) and `AuthService.refresh` now return it, as well as `GET /users/me`. The web client replaces its cached user on every token refresh (`refreshAuthState` in `apps/web/src/api.ts`). Without this, a confirmed user would see the gate again after each refresh.
4. **Push suppression covers four call sites**: `notifyMentionedUsers` is now called from `createMessage`, thread replies, forum posts (`forum-posts.service.ts`) and webhook delivery (`webhook-delivery.service.ts`). `isAgeRestricted` is a required input, so all four pass it. The webhook's authenticated channel select gained `isAgeRestricted`.
5. **Error code mapping is manual**: `npm run i18n:check` does not detect an exception message thrown through a constant. `'You must confirm your age to view this channel'` was added by hand to `common/i18n/error-codes.ts` and to both API locale catalogs, the same as `RULES_NOT_ACCEPTED_MESSAGE`.
6. **Extra web files**: `hooks/useAgeConfirmation.ts` (new; the confirm call, then a functional `setAuth` update), `hooks/useSettingsActions.ts` (sends `isAgeRestricted` from the settings form), `hooks/useChannelOpening.ts`, `AppShell.tsx`, `components/app/buildChatAndSettingsProps.ts`, `components/chat/AgeGate.module.css`, and `components/workspace/ChannelSidebar.module.css` (the `18+` badge). `ChatPanel` takes `confirmAge` as a top-level prop, not on `session`, because `CallStage` reuses the session shape for direct messages.
7. **Stage view is not gated on the client**: `AgeGate` replaces the forum view and the message list/composer. It does not replace `StageChannelView`, because stage audio is not message content and the stage endpoints do not go through `requireReadableChannel`.
8. **`channel:join` joins the server room before the age gate**: `MessagesGateway.joinChannel` checks `ViewChannel` (`RealtimeAccessService.requireChannelView`), joins `serverRoom`, then runs `requireAgeConfirmed` and acknowledges a refusal with the translated `{ error }` instead of throwing. `useChannelOpening` still emits `channel:join` while gated. Reason: a human socket joins server rooms only through `channel:join`, so an unconfirmed user whose first opened channel in a server was age-restricted received no server-wide events (presence, member, emoji, events updates) until they opened another channel. The server room carries no channel content, so the gate still protects everything inside the channel.
9. **Saved-message reminder pushes are suppressed too**: `ReminderSweepService` reads the source channel's current `isAgeRestricted` and, when set, sends the push with the generic `reminder.savedMessage.ageRestrictedBody` instead of author and content. The in-app notification row keeps the snapshot, as mention notifications do; only the push can show on a lock screen.
