# Channel View Eviction

- **Status**: draft — awaiting review
- **Date**: 2026-09-29
- **Related**: [`channel-live-settings-sync.md`](channel-live-settings-sync.md) (Scope → Out of scope), [`age-restricted-channels.md`](age-restricted-channels.md), [`open-questions.md`](open-questions.md) #55

## Goal

`open-questions.md` row #55 records: _"`ChannelsService.updateChannel` never evicts an already-joined socket from `channelRoom(channelId)` when a channel flips `isPrivate: true`, or when `updatePermissionOverrides` removes a member's `ViewChannel` (only the `isAgeRestricted` flip does, via `evictUnconfirmedMembers`) — a member who already has the channel open keeps receiving its live message events after losing REST access, until they reconnect."_ (`docs/features/open-questions.md:43`).

Verified directly against the code (not restated from the open-question row as fact):

- `ChannelsService.updateChannel` (`apps/api/src/modules/channels/channels.service.ts:77-125`) writes `isPrivate` (`:97`) and, only when the channel newly becomes age-restricted, calls `evictUnconfirmedMembers` (`:113-115`, defined `:215-224`). No branch reacts to `isPrivate` turning `true`; no `removeUsersFromRooms` call for it.
- `ChannelsService.updatePermissionOverrides` (`:146-180`) replaces every `ChannelPermissionOverride` row for the channel (`:161-175`) and calls neither `removeUsersFromRooms` nor any other realtime primitive.
- `evictUnconfirmedMembers` (`:215-224`) evicts on a completely different axis — `User.ageConfirmedAt`, not `VIEW_CHANNEL` — so it does not, and structurally cannot, cover this gap.
- The single source of truth for "can this member view this channel" is `evaluateChannelPermission` (`apps/api/src/modules/permissions/channel-permission.ts:47-79`), driven by role permissions, `channel.isPrivate`, and `ChannelPermissionOverride` rows, and already batched by `PermissionsService.filterMembersWhoCanView` (`permissions.service.ts:179-194`) and `filterViewableChannels` (`:152-176`). Nothing here calls into the realtime layer — this doc's job is exactly that missing wiring.

This doc designs one general mechanism — recompute who currently holds `VIEW_CHANNEL` and evict everyone else's socket from the affected channel room(s) — reused by every write path that can remove `VIEW_CHANNEL`, instead of a per-feature patch repeating `evictUnconfirmedMembers`'s shape for each one.

**Acceptance criteria**:

- [ ] A member with a text channel's room joined stops receiving `message:created`/`message:updated`/`message:deleted`/`reaction:updated`/`typing:*`/`forum:post-created`/`decision:*` for that channel within the same request that revokes their `VIEW_CHANNEL`, for every write path listed in Scope → In scope.
- [ ] A member who still holds `VIEW_CHANNEL` after the write (unaffected member, `ManageChannels` holder, owner) is never evicted.
- [ ] Every socket of an affected user is evicted, not just one (a user with two open tabs).
- [ ] The write itself, and its existing behavior (audit log, `channel:updated` emission, response body, status codes), is unchanged — this doc only adds eviction.
- [ ] A write that grants `VIEW_CHANNEL` (or changes nothing about it) never evicts anyone.

## Scope

**In scope**

- A shared recompute-and-evict primitive, built on the existing `PermissionsService.filterMembersWhoCanView`/`filterViewableChannels` — no new permission-evaluation logic, no copy of `evaluateChannelPermission`.
- Wiring it into every write path confirmed (by reading the code, see Current behavior) to be able to remove a member's `VIEW_CHANNEL` on a channel that did not already fully remove their server membership:
  - `ChannelsService.updateChannel` — `isPrivate` flip (either direction, see Changes).
  - `ChannelsService.updatePermissionOverrides` — any override replacement.
  - `RolesService.updateRole` — a role's `permissions` array changed.
  - `RolesService.deleteRole` — a role removed (its `ChannelPermissionOverride` rows cascade-delete, `apps/api/prisma/models/channels.prisma:74`).
  - `RolesService.addMemberRole` / `RolesService.removeMemberRole` — a role added to or removed from one member (see Current behavior for why _adding_ a role can also remove `VIEW_CHANNEL`).
- Evicting every live socket of an affected user (multi-tab), using the existing `RealtimePublisher.removeUsersFromRooms` primitive (Socket.IO's `socketsLeave`, already cross-instance safe via the Redis adapter attached in `realtime.gateway.ts:58-59`).

**Out of scope**

- Any new client-visible event or UI refresh beyond what already exists. `updateChannel` already emits `channel:updated` unconditionally (`channels.service.ts:119-123`, added by `channel-live-settings-sync.md`), which already makes a losing member's sidebar/channel view refetch and drop the channel. `updatePermissionOverrides` and every role write path add **no** new client event — overrides are not surfaced in the UI today (`channel-live-settings-sync.md`, Scope → Out of scope, confirms this), and a role edit can touch many channels at once, which does not fit the one-channel-id payload `channel:updated` carries. The pre-existing "role/member permission change goes stale in the UI until reload" gap is not solved here; it is a UI-staleness problem, this doc is an authorization-consistency one (see Trade-offs, option B, for why the two are not conflated).
- `PresenceUpdate`/`typing:*` exclusion for bots — decided separately in `open-questions.md` #55... no, #31 (`docs/features/open-questions.md:65`, "bots keep receiving presence/typing… low-sensitivity"). That decision is about presence/typing being broadcast to the whole server room regardless of per-channel view; it does not apply here, because a bot socket _does_ join individual `channelRoom`s at connect (`realtime.gateway.ts:130-139`) and _is_ subject to the same `VIEW_CHANNEL` evaluation as a human member (`evaluateChannelPermission` has no `kind === 'BOT'` exemption — only `kind === 'OWNER'` short-circuits, `channel-permission.ts:55`). Bot sockets are therefore **included** in eviction, through a separate primitive (`removeBotFromRooms`, keyed by bot id, not `userRoom`) — see Changes and Edge cases.
- `Permission.KickMembers`-driven removal (`ServerModerationService.kick`/`ban`/`leave`, `server-moderation.service.ts:37-90,222-232`) — already evicts the removed user from every channel room of the server, unconditionally, via `announceRemoval` (`:212-232`). Membership itself is gone, so there is nothing to recompute; untouched by this doc.
- `MemberTimeout` (`server-moderation.service.ts:94-116`, `setMemberTimeout`) — `requireNotTimedOut` gates `SEND_MESSAGES`-shaped actions only (`messages.service.ts:205,322,422,517`, `polls.service.ts:161`, `soundboard-playback.service.ts:44`); it is never consulted for `VIEW_CHANNEL`. A timeout does not remove view access, so it is not a writer this doc needs to cover.
- Server deletion / ownership transfer (`server-ownership.service.ts`) — deletion already evicts every member from every room of the server (`:120-135`); ownership transfer changes no member's `VIEW_CHANNEL` (the owner bypass in `evaluateChannelPermission:55` moves with the `kind` field, not with a specific user, and only one member holds `OWNER` at a time either way). Neither needs this mechanism.
- Voice/stage call participation. `voice:join`'s authorization (`RealtimeAccessService.authorizeCallJoin` → `requireChannelMember`, `realtime-access.service.ts:107-119`) checks server membership only, not `VIEW_CHANNEL` — a pre-existing gap, unrelated to and not widened or narrowed by this doc. A member already in a channel's call keeps their call participant row untouched; only the channel's **text** room (`channelRoom(channelId)`, used for `message:*`/`reaction:*`/`typing:*`/`forum:*`/`decision:*`) is affected, because that is the room this mechanism evicts from.
- Retroactively closing the "socket in `channelRoom` before eviction still receives a message broadcast in flight" race any tighter than `evictUnconfirmedMembers` already accepts today (see Risks).

This confirms the open-question's framing was accurate for `updateChannel`/`updatePermissionOverrides`, and reading the rest of the write surface shows the gap is wider: every role-mutation path in `apps/api/src/modules/roles/roles.service.ts` (`:51-136`) never imports `RealtimePublisher` at all — a rule enforced in some write paths (kick/ban/age-restriction) and not others is not enforced (`~/.claude/rules/failure-and-state.md`, "Invariants").

Two structural facts make a **general** mechanism possible instead of five bespoke patches:

- `evaluateChannelPermission` (`channel-permission.ts:47-79`) is the single, pure (no I/O), already-shared evaluator every one of these paths ultimately feeds.
- `PermissionsService.filterMembersWhoCanView(channel, members)` (`permissions.service.ts:179-194`) and `filterViewableChannels(userId, channels)` (`:152-176`) already batch that evaluator against a channel's members or a user's channels with a bounded number of queries (one members query, one overrides query) — the exact shape `RealtimeUnreadService.listUnreadRecipients` already reuses per message send (`realtime-unread.service.ts:48-74`), at far higher frequency than any permission-changing write. That existing call site is the cost baseline for this doc (see Trade-offs).

## Changes

### Rules / Flow

1. A new `RealtimeViewEvictionService` (realtime module) exposes three methods, each a thin composition of an existing `PermissionsService` query plus `RealtimePublisher.removeUsersFromRooms`/`removeBotFromRooms` — no new permission logic:
   - `evictChannel(channelId: string)`: loads the channel and every member of its server (with roles), calls `permissions.filterMembersWhoCanView(channel, members)`, and evicts the complement (`members` minus the viewers) from `channelRoom(channelId)`. Human members go through `removeUsersFromRooms([...userIds], [channelRoom])`; members with `kind === 'BOT'` go through `removeBotFromRooms(botId, [channelRoom])` (bots never join `userRoom`, confirmed by the existing comment at `server-moderation.service.ts:229-230` and `bot-gateway-sync.ts:9`, so `removeUsersFromRooms` alone would silently skip them).
   - `evictServerForRole(serverId: string, roleId: string)`: loads every channel of the server and every member currently holding `roleId` (with roles), then calls the same per-channel filter/evict for each channel, scoped to just those members. Scoped to role holders, not the whole server, because only they can possibly be affected by that role's permissions or overrides changing.
   - `evictMember(serverId: string, userId: string)`: loads the member (with roles) and every channel of the server, calls `permissions.filterViewableChannels(userId, channels)` (already exists, already used for exactly "which channels can this one user see" in `RealtimeAccessService.listViewableChannelIds`, `realtime-access.service.ts:91-101`), and evicts that one user from every channel **not** in the viewable set.
2. Call sites, all **after** the write commits (persist first, evict second — the same ordering `updateChannel` already uses for `evictUnconfirmedMembers` and `channel:updated`, `channels.service.ts:113-123`):
   - `ChannelsService.updateChannel`: `if (dto.isPrivate !== undefined) await this.viewEviction.evictChannel(channel.id);` — placed before the existing `channel:updated` emit, so a client that refetches on that event cannot re-join `channel:join` a room its socket was never told to leave.
   - `ChannelsService.updatePermissionOverrides`: `await this.viewEviction.evictChannel(channelId);` unconditionally, after the `$transaction` that replaces the overrides — this endpoint's only purpose is changing overrides, so there is no cheaper condition to gate on.
   - `RolesService.updateRole`: `if (dto.permissions !== undefined) await this.viewEviction.evictServerForRole(existing.serverId, roleId);` — after the `prisma.role.update`.
   - `RolesService.deleteRole`: capture `existing.serverId` and `roleId` before `prisma.role.delete`, call `evictServerForRole` after the delete commits (the cascade-deleted overrides are already gone from the DB by the time `filterMembersWhoCanView` runs, so the recompute reflects their absence correctly).
   - `RolesService.addMemberRole` / `removeMemberRole`: `await this.viewEviction.evictMember(serverId, member.userId);` after each `prisma.memberRole.upsert`/`deleteMany`.
3. No change to `evictUnconfirmedMembers`, `requireAgeConfirmed`, `requireViewableChannel`, or any other authorization check — this doc only adds a **realtime room membership** side effect after an already-authorized write; the actual authorization performed on every future request (`hasChannelPermission`, `requireChannelPermission`, `filterViewableChannels` in `getServerForUser`) is untouched and already correct. The gap being closed is that a socket already sitting in a room keeps receiving broadcast events for it regardless of what a fresh permission check would now say — this is a live-broadcast consistency fix, not a new authorization decision.
4. `evictChannel`/`evictServerForRole`/`evictMember` never special-case the actor, the owner, or a `ManageChannels` holder — none is needed. `evaluateChannelPermission` already returns `true` unconditionally for `member.kind === 'OWNER'` (`:55`) and, on a private channel, for anyone with role-level `ManageChannels` (`:58-60`) before it ever consults overrides — so the actor who just made themselves (or the owner) an exception through the normal permission model is, by construction, in the "still a viewer" set the recompute produces, and is never evicted.

### Edge cases

| Case                                                                                                                                                          | Expected behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The evicted member is the actor                                                                                                                               | Not specially handled and not expected: the actor holds `ManageChannels` (required to call `updateChannel`/`updatePermissionOverrides`/`updateRole`/`removeMemberRole`) or `ManageRoles`, and per Rules item 4 that already keeps them a viewer on a private channel. The only way an actor evicts themselves is an explicit self-targeted `memberId` override with `deny: ['VIEW_CHANNEL']` on a non-private channel where their role does not otherwise grant `ManageChannels`/`ViewChannel` — a deliberate, self-inflicted action the permission model already allows today with or without this doc; the recompute treats it exactly like any other member's loss. |
| `ManageChannels` holder or owner                                                                                                                              | Never evicted from a channel their own action just made private, or from any channel, per Rules item 4 — no special case needed in the eviction code itself.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| A member with the channel open, in a live voice/stage session for the same channel                                                                            | The call participant row (`CallRegistryService`) and `callRoom` membership are untouched — `voice:join`'s authorization does not check `VIEW_CHANNEL` today (Scope → Out of scope), so nothing about this doc changes their call state. Only their `channelRoom` (text events) membership is affected, matching how `evictUnconfirmedMembers` already treats the same overlap for age-restriction.                                                                                                                                                                                                                                                                     |
| Multiple sockets for one user (two tabs)                                                                                                                      | `removeUsersFromRooms`/`removeBotFromRooms` operate on `server.in(userRoom(userId))`/`server.in(botRoom(botId))`, which every live socket of that identity joined at connect (`realtime.gateway.ts:95,135`) — `socketsLeave` removes the room from every one of them in a single call, cross-instance via the Redis adapter.                                                                                                                                                                                                                                                                                                                                           |
| Bot socket                                                                                                                                                    | Included (see Scope → Out of scope, reversing the presumption from `open-questions.md` #31): a bot's `channelRoom` membership is computed the same way a human's is, and it is evicted through `removeBotFromRooms`, not `removeUsersFromRooms`, because a bot socket never joins `userRoom` (`bot-gateway-sync.ts:9`, `server-moderation.service.ts:229-230`).                                                                                                                                                                                                                                                                                                        |
| A write that only grants `VIEW_CHANNEL` (e.g. `isPrivate: true → false`, an `allow` override added, `addMemberRole` granting a role with no denying override) | `evictChannel`/`evictServerForRole`/`evictMember` still run (per Rules item 2, unconditioned on direction) and still call `removeUsersFromRooms` — but only for members who fail the recomputed check, which is nobody in this case; `socketsLeave` is a no-op for a room a socket already is not in and for an empty user list the primitives already short-circuit (`realtime-publisher.service.ts:41-42`). No harmful side effect from running the mechanism unconditionally on any `isPrivate`/override/role/membership write, regardless of direction.                                                                                                            |
| Channel has zero members with a live socket (nobody currently has it open)                                                                                    | `removeUsersFromRooms`/`removeBotFromRooms` no-op silently; `Server.in(...).socketsLeave(...)` on an empty target room is inexpensive and side-effect-free.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Two permission-affecting writes to the same channel in quick succession                                                                                       | Each write's `evictChannel` call is independent and idempotent — the second call's recompute reflects both writes' cumulative state (the first write already committed by the time the second one's `updateChannel`/`updatePermissionOverrides` call starts, since both go through the same row-level Postgres transaction semantics as today), so there is no possible "stale" eviction from running two of these back to back.                                                                                                                                                                                                                                       |
| A permission-removing write committing while a `message:created` broadcast for that channel is already in flight                                              | Accepted, unresolved race, same shape `evictUnconfirmedMembers` already accepts for age-restriction: `emitToRoom` and `removeUsersFromRooms` are both fire-and-forget Socket.IO calls with no ordering guarantee against a broadcast already dispatched to the room a moment earlier. A socket evicted a few milliseconds after a message was broadcast to its (still current, at broadcast time) room membership will have received that one message. This is inherent to room-based fire-and-forget broadcast and not solved by this doc — see Risks.                                                                                                                |

**API contract**

- No REST endpoint, request, or response shape changes. Every affected endpoint (`PATCH /channels/:channelId`, the overrides endpoint, the role endpoints) keeps its existing status codes; the new eviction call happens after the existing success path and cannot itself produce a new error response to the caller (a realtime-layer failure would need to be handled the way `emitToRoom`/`removeUsersFromRooms` already are today — see Risks).
- No new socket event carries data. The only realtime-visible effect is socket **room membership** changing (`socketsLeave`), which produces no packet the evicted client can inspect; the client learns about the underlying change only through the pre-existing `channel:updated` event (for `updateChannel`) or, for overrides/role changes, not at all until it separately refetches — unchanged from today, per Scope → Out of scope.

**DB / migration**

- None. No schema change; this doc adds realtime-layer side effects to existing writes, using existing tables and existing query helpers.

**Libraries** — none new; reuses `PermissionsService`, `RealtimePublisher`, and the already-attached `@socket.io/redis-adapter` (`realtime.gateway.ts:58-59`).

## Trade-offs

| Option                                                                                                                                                                                        | Pros                                                                                                                                                                                                                                                                             | Cons                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Verdict                                                                                                                                                                                                                                                   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A (chosen): a shared `RealtimeViewEvictionService`, built on the existing `filterMembersWhoCanView`/`filterViewableChannels`, called from every write path that can remove `VIEW_CHANNEL`** | One mechanism instead of five near-identical patches; reuses the same evaluator and batching every other viewability check already trusts, so it cannot drift from REST's own authorization; server-side `socketsLeave` is a real enforcement, not a hint the client can ignore. | Every one of the five write paths pays one extra query pair (members+roles, overrides) per call — see cost analysis below. `evictServerForRole`/`evictMember` walk every channel of the server in-process (pure `evaluateChannelPermission` calls, no extra DB round trip per channel), which is unproven at very large channel/member counts (see Risks — "not verified" call-out).                                                                                                                                                                                                                                                                                                                                                 | Chosen — smallest change that reuses existing infrastructure and closes the gap for every writer identified in Current behavior, not just the two named in the open question.                                                                             |
| B: broadcast a "permissions changed, re-verify yourself" event and let the client leave the room / stop rendering                                                                             | No server-side recompute at all; cheapest possible backend change.                                                                                                                                                                                                               | **Not a security control.** The socket keeps receiving `message:created`/etc. from the room until the client's own JS chooses to act on the notification — a modified or slow client (or one that simply has not processed the event yet) keeps reading channel content it has already lost `VIEW_CHANNEL` for. This inverts the trust model the rest of this app uses (`~/.claude/rules/security.md`, "Hiding a button in the UI is not authorization"): eviction from a Socket.IO room is a server-enforced fact; a client-obeyed notification is not. Rejected as the enforcement mechanism; nothing here prevents it being added later as a purely cosmetic nudge alongside the real eviction, but that is not part of this doc. |
| C: per-feature patches — copy `evictUnconfirmedMembers`'s shape into `updateChannel` for `isPrivate`, into `updatePermissionOverrides`, and into each of the four role-mutation methods       | No new shared service or module to wire up; each patch is small and localized.                                                                                                                                                                                                   | Five near-identical query-and-evict blocks, each one an opportunity to compute viewability slightly differently (e.g. forgetting the bot-room distinction, or forgetting that `addMemberRole` can also revoke access) — exactly the "rule enforced in one of three write paths is not enforced" failure this doc exists to avoid. Any future sixth writer (a new override endpoint, a future bulk-role-assignment feature) would need yet another copy instead of one more call site.                                                                                                                                                                                                                                                | Rejected — the task explicitly asks for one general mechanism, and the five call sites already found are similar enough that a shared primitive is justified on the third occurrence and beyond (`~/.claude/rules/code-design.md`, "rule of three").      |
| D: recompute for the entire server on every write (ignore role/channel scoping, always walk every channel × every member)                                                                     | Simplest possible implementation — one function, no distinction between "channel-scoped" and "role-scoped" writers.                                                                                                                                                              | Wastes work: a single-channel `isPrivate` flip does not need to re-evaluate every other channel in the server; a role held by 5 members out of 10,000 does not need every non-holder re-checked. At a large server this turns every permission-affecting write into an O(channels × members) operation instead of the tighter O(members) (`evictChannel`) or O(channels × role-holders) (`evictServerForRole`) this doc's design achieves.                                                                                                                                                                                                                                                                                           | Rejected — the scoped design (per-channel for channel-level writes, per-role-holder-set for role writes, per-user for membership writes) costs strictly less for the same correctness, with no added complexity beyond three method names instead of one. |

**What the chosen option costs**: one extra query pair (server members with roles, plus channel overrides) per `updateChannel`(`isPrivate`)/`updatePermissionOverrides` call, and a bounded in-process loop over the server's channels for the two role-mutation-adjacent writers. This is the same query shape `RealtimeUnreadService.listUnreadRecipients` already runs **per message sent** (`realtime-unread.service.ts:48-74`) — a much higher-frequency code path than any of the writes this doc touches (channel settings, overrides, and role edits are all infrequent, `ManageRoles`/`ManageChannels`-gated administrative actions). No caching or invalidation scheme is introduced; each call re-reads current state, which is the only way to guarantee the recompute reflects the write that just committed.

**What is not proven, and is called out as such rather than guessed** (`~/.claude/rules/ai-pitfalls.md`): the actual latency/CPU cost of `evictServerForRole`/`evictMember` at a large member or channel count. No server-member cap or channel-count cap was found anywhere in this repo (`grep` for a member/channel limit returned nothing memberlist-shaped); `evaluateChannelPermission` itself is a handful of array operations with no I/O, so the in-process loop is CPU-bound, not DB-bound, but this repo has no test suite and no load-testing harness to measure it against (`package.json` scripts: `dev`, `build`, `lint`, `typecheck`, `format`, `i18n:check`, `ui:scan`, `ui:smoke` — no `test`). This is recorded as an open question below rather than asserted either way.

## Risks & rollback

- **What can break**: nothing in the write paths' own persisted behavior — the eviction call is purely additive and happens after the existing `prisma` write and (for `updateChannel`) before the existing `channel:updated` emit, so ordering with that event is preserved. A bug in the new service could over-evict (a false negative in "who can view") or under-evict (a false positive); both are contained to realtime room membership, not to the underlying REST authorization, which remains correct regardless (a future `GET`/`channel:join` still re-evaluates `VIEW_CHANNEL` from scratch).
- **Not covered**:
  - The broadcast-in-flight race described in Edge cases (a message dispatched to the room a moment before eviction still reaches the now-unauthorized socket once). Pre-existing shape, same as `evictUnconfirmedMembers` today; not solved here.
  - The UI-staleness half of this problem for overrides and role changes (Scope → Out of scope) — a member who loses `VIEW_CHANNEL` via a role edit stops receiving events immediately, but their sidebar/open channel does not know to disappear until they separately refetch. Recorded, not solved, matching the same split `channel-live-settings-sync.md` already drew between "authorization-consistency" and "UI-staleness" for the `isPrivate` case.
  - Cost at very large member/channel counts (see Trade-offs, "What is not proven").
- **Rollback**: revert the code. No migration, no persisted data to unwind — the new service and its five call sites are removed together, returning every write path to today's "no eviction beyond age-restriction" behavior exactly. Nothing here changes a stored value, only a live, non-persisted Socket.IO room membership.

## Test plan

Not covered by automated tests — the repo has no test suite (`package.json` scripts at the root and in `apps/api`/`apps/web`: `dev`, `build`, `lint`, `typecheck`, `format`, `i18n:check`, `ui:scan`, `ui:smoke`; no `test` script anywhere).

**Manual**

1. Two browser sessions in the same server: tab A as a member with `VIEW_CHANNEL` via a role only (no override, not `ManageChannels`), with a text channel open; tab B as a `ManageChannels` holder. In tab B, `PATCH` the channel's `isPrivate` to `true` with no override compensating tab A's role. Post a message from a third session that still has access → tab A does not receive `message:created` for it (room eviction happened on the `PATCH`, before the post).
2. Same setup as (1), but tab A's role holds `ManageChannels` → after the same `PATCH`, post another message → tab A still receives it (not evicted, per Rules item 4).
3. Tab A open on a channel with `VIEW_CHANNEL` via a role and no override; tab B (a `ManageRoles` holder) adds a `ChannelPermissionOverride` for that role with `deny: ['VIEW_CHANNEL']` on that channel via `updatePermissionOverrides`. Post a message → tab A does not receive it.
4. **(Corrected after implementation — the original step was not runnable.)** This step used to say "remove `VIEW_CHANNEL` from `@everyone`'s `permissions` via `updateRole`", but `findMutableRole` refuses that outright (`ForbiddenException('Cannot mutate @everyone role')`, `apps/api/src/modules/roles/roles.service.ts:279-280`), so the scenario could never be executed as written. The runnable equivalent, which is what was actually verified: put tab A on a **private** channel it can see only through Role X's `MANAGE_CHANNELS`, then have tab B strip that permission from Role X via `updateRole`. Post a message → tab A does not receive it. A private channel is required because, while `@everyone` still grants `VIEW_CHANNEL` and cannot be edited, a non-private channel's visibility can never be revoked through a role's base permissions at all. Repeat with `deleteRole` on that same role — same expected result.
5. Tab A open on a channel visible only through Role X; tab B removes Role X from tab A's member via `removeMemberRole` → tab A stops receiving events for that channel, while a different channel tab A can still see (via `@everyone`) keeps delivering.
6. Two tabs (A1, A2) open as the same user on the same channel; tab B revokes access as in (1) → neither A1 nor A2 receives the next message.
7. A bot with a channel open (connected via the bot gateway) loses `VIEW_CHANNEL` through the same `isPrivate` flip as (1) → verify (via the bot's own event log, or `apps/api` logs if the bot process logs received events) that it stops receiving events for that channel; a second bot unaffected by the change keeps receiving them.
8. **Failure case**: an actor without `ManageChannels`/`ManageRoles` attempts any of the above writes → `403`, unchanged; confirm no eviction-related side effect occurs for a rejected write (the eviction call is unreachable after the permission check throws, same as the existing `channel:updated` emit).
9. A write that only grants access (`isPrivate: true → false`, an `allow` override added) with tab A already able to view the channel before the change → tab A keeps receiving events throughout, uninterrupted (no accidental eviction of a still-authorized viewer).

## Deviations

- **`RolesService.deleteRole` cannot call `evictServerForRole(serverId, roleId)` after the delete commits, as originally planned.** `MemberRole.role` cascades on `Role` delete (`apps/api/prisma/models/servers.prisma:158-165`, `onDelete: Cascade`), so the join rows linking members to `roleId` are already gone by the time `evictServerForRole`'s `loadRoleHolders(serverId, roleId)` query runs — it would find zero holders and silently evict nobody, defeating the purpose for every `deleteRole` call. (`ChannelPermissionOverride.role` also cascades the same way, `channels.prisma:74`, which is fine — that part of the original reasoning, "the cascade-deleted overrides are already gone from the DB by the time `filterMembersWhoCanView` runs", was correct; the join-row cascade on the holder lookup itself was the part missed.)
  - **Fix**: `deleteRole` captures the role's holder `userId`s with a `serverMember.findMany({ where: { serverId, roles: { some: { roleId } } }, select: { userId: true } })` query **before** `prisma.role.delete`, then — after the delete and its audit log — calls the existing `evictMember(serverId, userId)` once per captured holder (`Promise.all`, independent I/O per `~/.claude/rules/performance.md`), instead of `evictServerForRole`. `evictMember` re-reads each member's current roles and every channel of the server, so it correctly reflects the role's removal (the member's role list no longer includes it) without depending on a join row that is already gone.
  - This reuses the three methods exactly as designed — no fourth method added — at the cost of one `evictMember` call (its own two-query recompute) per holder instead of one shared per-channel batch; `deleteRole` is an infrequent, `ManageRoles`-gated administrative action, so this is the same "infrequent write, existing query shape" cost argument as the rest of Trade-offs.
  - `evictServerForRole` itself is unchanged and still used as designed by `updateRole`, where the role is not deleted and its `MemberRole` join rows still exist at call time.
