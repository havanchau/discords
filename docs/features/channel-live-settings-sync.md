# Live Channel Settings Sync

- **Status**: draft — awaiting review
- **Date**: 2026-09-25
- **Related**: [`age-restricted-channels.md`](age-restricted-channels.md), [`open-questions.md`](open-questions.md) #49

## Goal

There is no `channel:updated` socket event anywhere in the codebase (`grep -rn "channel:updated" apps/ packages/` — no matches). When a `ManageChannels` holder changes a channel's settings — name, topic, `isPrivate`, `isAgeRestricted`, `slowmodeSeconds`, category, `postGuidelines`, avatar — every client except the one that made the change keeps its stale copy until it reopens the channel or reloads the page. `open-questions.md` #49 named this gap during `age-restricted-channels.md` and deferred it: _"Decided 2026-09-22: accept 'stale until reopen'; live settings sync is its own feature"_ (`docs/features/open-questions.md:37`). This doc is that feature.

Concretely, today:

- The actor who saves the change sees it immediately, because `useSettingsActions.updateChannelSettings` patches its own React Query cache directly after the `PATCH` response (`apps/web/src/hooks/useSettingsActions.ts:525-530`).
- No other client — a second tab, a second member, a member with the channel not open — learns about the change until it independently refetches `GET /servers/:id`.
- For age-restriction specifically, the socket room eviction already works (`ChannelsService.updateChannel` calls `evictUnconfirmedMembers` when a channel flips to restricted, `apps/api/src/modules/channels/channels.service.ts:109-111,194-203`), but the affected member's already-rendered message list "goes stale until they navigate away and back" — the exact sentence recorded in `age-restricted-channels.md`'s edge-case table (`docs/features/age-restricted-channels.md:97`).

**Acceptance criteria**:

- [ ] Saving any field via `PATCH /channels/:channelId` (`ChannelsService.updateChannel`) emits a `channel:updated` event that every other member with that server's socket room joined receives.
- [ ] A member with the channel open sees its name/topic/slowmode/"18+" badge update without reloading or reopening the channel.
- [ ] A member who has the channel open when it flips to `isAgeRestricted: true` sees the age gate render in place of the message list without reopening the channel — closing the exact gap recorded in `age-restricted-channels.md`'s edge-case table.
- [ ] A member who is not a member of the channel's server, or who cannot view a private channel, never receives channel field values through the event payload.
- [ ] A member who loses `ViewChannel` on a channel that becomes private sees it disappear from their sidebar without reloading.

## Scope

**In scope**

- A new socket event `channel:updated`, emitted by `ChannelsService.updateChannel` to the channel's server room, carrying only `{ serverId, channelId }` — no setting values in the payload.
- A web listener that invalidates the `serverDetail` React Query cache for that server on receipt, the same reaction `server:onboarding-updated` already gets (`apps/web/src/hooks/useServerModeration.ts:154-158`).
- Verifying (not re-implementing) that this refetch alone is sufficient to update every place a channel's fields are read on the client, because `channel` and the sidebar list are both derived from the same `server.channels` array (see Current behavior).

**Out of scope**

- Any new socket-room eviction logic beyond what `age-restricted-channels.md` already built. Flipping `isPrivate: true` or changing `ChannelPermissionOverride` rows does **not** evict an already-joined socket from the channel room today (`ChannelsService.updateChannel`, `apps/api/src/modules/channels/channels.service.ts:73-113`, and `updatePermissionOverrides`, `:134-168`, neither calls `removeUsersFromRooms`) — only the age-restriction flip does. A member who already had the channel's room joined before it went private keeps receiving `message:created`/`reaction:updated`/`typing:*` for it until they leave and rejoin, or reconnect. This is the same shape of gap `age-restricted-channels.md` left for rules-screening (`docs/features/age-restricted-channels.md:37`), now also true for privacy changes; it is a live authorization-consistency problem, not a UI-staleness one, and needs its own doc to scope who computes "which currently-joined sockets just lost `ViewChannel`" across every override combination. Recorded as a risk below and as an open question.
- Channel deletion — there is no `DELETE /channels/:channelId` endpoint in the repo (`grep -rn "channel.delete\|deleteChannel" apps/api/src` — no matches); channels cannot be deleted today, so there is no "channel deleted" case to sync.
- Channel creation and category/position reordering broadcasts — `CategoriesService` and `createChannel` are not touched; a created channel is already returned synchronously to its creator and picked up by anyone else only on their next `serverDetail` fetch, unchanged by this doc. Only `updateChannel`'s existing write path gains the new event.
- `ChannelsService.updatePermissionOverrides` (`:134-168`) emitting its own event — overrides are not surfaced anywhere in `ChannelList.tsx`/the gate components today, so there is nothing visible to go stale; adding sync for overrides is deferred to whoever picks up the eviction gap above, since the two are the same problem.
- A dedicated `channel-overrides` / `channelWebhooks` query-key invalidation — those are fetched on demand when the overrides/webhooks panel opens (`queryKeys.channelOverrides`, `queryKeys.channelWebhooks`, `apps/web/src/query/queryKeys.ts:47-48`) and are not part of this doc's payload.

## Current behavior

- `ChannelsService.updateChannel` (`apps/api/src/modules/channels/channels.service.ts:73-113`) is the **only** write path for channel settings: `PATCH /channels/:channelId` → `ChannelsController.update` (`apps/api/src/modules/channels/channels.controller.ts:33-39`) → this method. It requires `Permission.ManageChannels` (`:78-82`), updates `name`, `topic`, `avatarUrl`, `isPrivate`, `isAgeRestricted`, `position`, `slowmodeSeconds`, `categoryId`, `postGuidelines` in one `prisma.channel.update` (`:87-100`), writes an audit log (`:101-108`), and — only for the age-restriction case — calls `evictUnconfirmedMembers` (`:109-111`, defined `:194-203`) which uses `RealtimePublisher.removeUsersFromRooms` to kick unconfirmed members' sockets out of `channelRoom(channelId)`. No socket event of any kind is emitted for the update itself.
- The realtime event catalog (`packages/shared/src/realtime-events.ts:35-79`) has no `channel:updated` entry. The nearest precedent for "a config object changed, tell clients to refetch it" is `ServerOnboardingUpdated: 'server:onboarding-updated'` (`:44`), emitted to `realtime.serverRoom(serverId)` with payload `{ serverId }` right after the DB write (`server-onboarding.service.ts:93-98`, comment: _"Persist first, emit second. Open tabs refetch the server detail…"_). `ServerEmojisUpdated`/`ServerStickersUpdated`/`ServerSoundboardUpdated` follow the same "id-only payload, client refetches" shape for their own resources.
- A human socket does **not** join a server's room at connect — only `userRoom(userId)` and DM conversation rooms (`apps/api/src/modules/realtime/realtime.gateway.ts:91-93`). It joins `serverRoom(serverId)` as a side effect of `channel:join`, the first time it opens any channel of that server (`apps/api/src/modules/realtime/messages.gateway.ts:38-46`, specifically line 45 `await client.join(this.publisher.serverRoom(channel.serverId))`, which runs before the channel's own age-gate check so server-wide events always reach a socket that has opened at least one channel). This means a member who has connected but never opened a channel in that server will not receive `channel:updated` until they do — the same pre-existing gap `server:onboarding-updated`/`server:member-updated` already have; not introduced or fixed here.
- `GET /servers/:serverId` (`ServersService.getServerForUser`, `apps/api/src/modules/servers/servers.service.ts:85-136`) filters `server.channels` through `PermissionsService.filterViewableChannels` (`:132`, same helper `listForUser` uses at `:70-77`) before returning — a member who cannot view a channel never receives its row, private or not. This is what makes an id-only `channel:updated` payload safe: the event never carries settings, and the refetch it triggers re-applies the same visibility filter that already governs the channel list today.
- Client state: `useWorkspaceStore` holds the server detail in React Query under `queryKeys.serverDetail(serverId)` (`apps/web/src/query/useWorkspaceStore.ts:67,85-92`) and derives the open channel from it — `const channel = useMemo(() => server?.channels.find((item) => item.id === activeChannelId) ?? null, [server, activeChannelId])` (`:97-100`). The comment above it states the intent directly: _"`channel` is derived rather than stored… so it can no longer disagree with the copy inside `server.channels`"_ (`:23-25`). There is also an effect that drops `activeChannelId` back to another channel when the active one disappears from `server.channels` (`:166-180`) — already wired for the "channel removed from the visible list" case.
- Every client read of channel fields already goes through this derived `channel`/`server.channels`, not a separate cache: the "18+" badge (`apps/web/src/components/workspace/ChannelList.tsx:137-141`, `channel.isAgeRestricted`), the age gate (`AppShell.tsx` computing `isAgeGated` from `channelNeedsAgeConfirmation(channel, auth.user)`, per `age-restricted-channels.md`'s Deviation 2), and `ChannelSettings.tsx`'s form fields all read the same `channel`/`server` objects. So refetching `serverDetail` is, by construction, enough to update all of them — no separate per-widget patch is needed.
- `useChannelOpening` already reacts to a change in gate state on the **same** channel id without a reconnect: its effect's dependency array includes `isAgeGated` (`apps/web/src/hooks/useChannelOpening.ts:151-153`, comment: _"or when the age gate lifts, which loads the messages and emits `channel:join` without a reconnect"_), and it also handles the reverse direction (gate newly applied) — `openChannel` checks `isAgeGated` first and, when true, clears messages and skips the fetch (`:75-82`). Since `isAgeGated` is computed from the same derived `channel` object, a `serverDetail` refetch that flips `isAgeRestricted` to `true` automatically re-runs this effect and renders the gate — **no new client wiring is needed for that specific case**, only the refetch trigger this doc adds.
- The only existing socket-driven `serverDetail` invalidators live in `useServerModeration.ts` (`apps/web/src/hooks/useServerModeration.ts:154-191`), wired into the app once in `AppShell.tsx:265` (`useServerModeration({...})`). `handleOnboardingUpdated` (`:154-158`) is the closest structural twin to what this doc adds.
- No test suite exists in this repo (`package.json` scripts: `dev`, `build`, `lint`, `typecheck`, `format`, `i18n:check`, `ui:scan`, `ui:smoke` — no `test` script at the root or in `apps/api`/`apps/web` `package.json`).

## Changes

### Rules / Flow

1. `RealtimeEvents` (`packages/shared/src/realtime-events.ts`) gains `ChannelUpdated: 'channel:updated'`, documented the same way as `ServerOnboardingUpdated`: `/** { serverId, channelId } after a channel's settings change; clients refetch the server detail. */`.
2. `ChannelsService.updateChannel` (`channels.service.ts:73-113`), right after the existing `evictUnconfirmedMembers` call (so eviction always lands before the client's refetch could re-join a room it should now be refused), emits: `this.realtime.emitToRoom(this.realtime.serverRoom(channel.serverId), RealtimeEvents.ChannelUpdated, { serverId: channel.serverId, channelId: channel.id })`. Emitted unconditionally on every successful update — the payload carries no field values, so there is no cost to emitting it for a cosmetic-only change (e.g. `topic` edit) the same way as for a security-relevant one (`isPrivate`, `isAgeRestricted`).
3. Web: `useServerModeration.ts` gains a `handleChannelUpdated` listener, structurally identical to `handleOnboardingUpdated` (`:154-158`): `(payload: { serverId: string; channelId: string }) => { void queryClient.invalidateQueries({ queryKey: queryKeys.serverDetail(payload.serverId) }); }`. Registered/unregistered alongside the existing `socket.on`/`socket.off` pairs (`:177-190`). `channelId` is accepted in the payload for future consumers (e.g. a component that only cares about one channel) even though this handler does not need it — matching the existing precedent that a payload documents the full change, not just what today's one reader uses (`MemberUpdatedPayload`, `:31-38`, is "partial by design").
4. No change to `ChannelsService.evictUnconfirmedMembers`, `RealtimeAccessService.requireViewableChannel`/`requireAgeConfirmed`, or any other authorization check — this doc only adds a notification, never a new authorization decision.

### Edge cases

| Case                                                                               | Expected behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Channel flipped to `isAgeRestricted: true` while an unconfirmed member has it open | Existing eviction (`evictUnconfirmedMembers`) removes their socket from the channel room; the new `channel:updated` event triggers their `serverDetail` refetch; `channel.isAgeRestricted` becomes `true` in the derived state; `isAgeGated` flips; `useChannelOpening`'s effect reruns and renders the age gate in place of the stale message list (Rules item 4 of `age-restricted-channels.md`'s mechanism, now triggered live instead of on next open).                                                                                           |
| Channel renamed / topic changed / slowmode changed while open                      | `channel:updated` → refetch → the derived `channel` object updates → any component reading `channel.name`/`channel.topic`/`channel.slowmodeSeconds` re-renders with the new value on its own next render, no extra code.                                                                                                                                                                                                                                                                                                                              |
| Channel flipped to `isPrivate: true`, viewer loses `ViewChannel`                   | The refetch's `filterViewableChannels` (`servers.service.ts:132`) excludes the channel from `server.channels`; the existing "active channel disappeared" effect (`useWorkspaceStore.ts:166-180`) moves them to another channel. Their socket, if it already had the channel's room joined, is **not** evicted by this change (see Scope → Out of scope) — it keeps receiving that channel's live message events until it reconnects or the room membership is otherwise cleared; only the UI (sidebar, active channel) reflects the loss immediately. |
| Non-member of the server / socket that never opened a channel in this server       | Never in `serverRoom(serverId)`, so `channel:updated` is never delivered to them — matches the pre-existing server-room-join gap documented above, not introduced here.                                                                                                                                                                                                                                                                                                                                                                               |
| Private channel, viewer without access                                             | Never receives `channel:updated` with meaningful information beyond an id already scoped to a server they belong to; a refetch triggered for a channel they cannot view simply returns the same `server.channels` list as before (the channel was never in it). No setting value is ever in the payload, so there is nothing to leak even if delivery reached a non-viewer.                                                                                                                                                                           |
| Two settings changes in quick succession (e.g. rename then re-rename)              | Each `PATCH` emits its own event; `invalidateQueries` on the second call coalesces with React Query's own request de-duplication — the client ends up with the latest persisted state, never an intermediate one, since it always refetches rather than applying the payload as a patch.                                                                                                                                                                                                                                                              |
| Unauthorized `PATCH` attempt (no `ManageChannels`)                                 | `403`, unchanged (`requireServerPermission`, `:78-82`); `updateChannel` throws before reaching the new emit, so no event is sent for a rejected write.                                                                                                                                                                                                                                                                                                                                                                                                |

## Technical approach

**Files touched**

| File                                                | Change                                                                                                                                                                                                          |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/shared/src/realtime-events.ts`            | Add `ChannelUpdated: 'channel:updated'` to `RealtimeEvents`, with a doc comment matching the existing style.                                                                                                    |
| `apps/api/src/modules/channels/channels.service.ts` | `updateChannel` emits `RealtimeEvents.ChannelUpdated` to `serverRoom(channel.serverId)` after the existing eviction call. Import `RealtimeEvents` from `@discord-clone/shared` (not yet imported in this file). |
| `apps/web/src/hooks/useServerModeration.ts`         | Add `handleChannelUpdated`, `socket.on`/`socket.off` registration, alongside the existing handlers (`:154-191`).                                                                                                |
| `docs/features/age-restricted-channels.md`          | Edge-case row at line 97 updated to note the gap is closed by this doc (cross-reference), once implemented.                                                                                                     |

**API contract**

- No REST endpoint changes. `PATCH /channels/:channelId` keeps its existing request/response shape and status codes (`400`/`403`/`404`, unchanged).
- Socket event `channel:updated` (new)
  - Direction: server → clients in `serverRoom(serverId)`.
  - Payload: `{ serverId: string; channelId: string }` — no setting values.
  - Emitted from: `ChannelsService.updateChannel`, after every successful `PATCH /channels/:channelId`.
  - No acknowledgment; fire-and-forget, matching every other `*:updated` broadcast in this catalog.

**DB / migration**

- None. No schema change.

**Libraries** — none new; reuses the existing `RealtimePublisher.emitToRoom` and the client's existing `socket.io-client`/React Query wiring.

## Trade-offs

| Option                                                                                                                                 | Pros                                                                                                                                                                                                                                                                                                                                                              | Cons                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Verdict                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A (chosen): dedicated `channel:updated` event, id-only payload, client refetches `serverDetail`**                                    | Reuses the exact pattern already proven for `server:onboarding-updated`/`server:emojis-updated`; payload carries no data to leak, so it is safe to broadcast to the whole server room without a per-recipient authorization check on the event itself; the client-side work is a five-line handler because every consumer already derives from `server.channels`. | One extra socket round trip and one extra `GET /servers/:id` per settings change, for every open client in that server, even ones not viewing the changed channel.                                                                                                                                                                                                                                                                                                          | Chosen — smallest change that closes the gap `open-questions.md` #49 named, reusing infrastructure this repo already trusts for the same shape of problem.                                                                                                 |
| B: put the full updated `Channel` object in the event payload, client patches its cache directly (`patchServer`) instead of refetching | No extra HTTP round trip; matches how the _actor's own_ client already updates optimistically (`useSettingsActions.ts:525-530`).                                                                                                                                                                                                                                  | Broadcasting full channel fields to every socket in `serverRoom(serverId)` — including members who cannot view a _private_ channel, since server-room membership is not scoped to per-channel visibility — would leak that private channel's name/topic/settings to non-viewers. Fixing that would require re-deriving per-recipient visibility at emit time (querying `filterViewableChannels` per connected socket), which the existing `emitToRoom` primitive cannot do. | Rejected — the leak this doc explicitly must not introduce (per the task's stated requirement); id-only + refetch reuses the server's own existing authorization instead of re-implementing it at the socket layer.                                        |
| C: poll `GET /servers/:id` periodically on the client instead of adding a socket event                                                 | No backend change at all.                                                                                                                                                                                                                                                                                                                                         | Either wastes requests when nothing changed, or is slow enough (any interval long enough to be cheap) that the "flip to age-restricted while open" acceptance criterion is not met in practice; also inconsistent with how every other live-updating piece of this app (messages, presence, member changes) already works.                                                                                                                                                  | Rejected — contradicts the repo's established realtime-first pattern and cannot meet the acceptance criteria at a reasonable interval.                                                                                                                     |
| D: emit to `channelRoom(channelId)` instead of `serverRoom(serverId)`                                                                  | Scoped exactly to members who currently have the channel open — no event reaches someone who never opened it.                                                                                                                                                                                                                                                     | Misses the sidebar-badge / "channel renamed while collapsed in the sidebar" and "channel appears/disappears from the list" cases, since a member who has not opened the channel is never in `channelRoom(channelId)` (only `channel:join` puts a socket there) — exactly the case Acceptance Criterion 5 (private-channel disappearance) needs to reach.                                                                                                                    | Rejected — `serverRoom` is the only room a member is reliably in once they have opened any channel in that server, matching the precedent `server:onboarding-updated` already uses for the same "affects the whole server's channel list" shape of change. |

What the chosen option costs: one extra `GET /servers/:id` per open client per settings change (not per message — settings changes are rare compared to messages), and the pre-existing "socket never evicted from a channel room on a privacy flip" gap (Scope → Out of scope) remains unresolved; this doc makes the UI consistent with the server's authoritative state faster, it does not add new authorization enforcement.

## Risks & rollback

- **What can break**: nothing existing — this is a strictly additive event with no new authorization check and no change to `updateChannel`'s persisted data. The only new client behavior is an extra cache invalidation.
- **Not covered**: socket-room eviction for a privacy flip or an override change (see Scope → Out of scope) — a member whose socket is already joined to a channel's room keeps receiving its live message events after losing `ViewChannel` via `isPrivate` or an override, until they reconnect. This is a pre-existing gap, unrelated to whether `channel:updated` exists, and is not introduced or worsened by this change.
- **Rollback**: revert the code. No migration, no persisted data to unwind — removing the event and the listener returns the app to today's "stale until reopen" behavior exactly.

## Test plan

Not covered by automated tests (repo has no test suite — confirmed via `package.json` scripts at the root and in `apps/api`/`apps/web`).

**Manual**

1. Open the same server in two browser sessions (or two tabs) as two different members, both with `ManageChannels` for one of them. In tab A, open a text channel. In tab B (the `ManageChannels` holder), `PATCH` the channel's `topic` via `ChannelSettings.tsx` → within one refetch cycle, tab A's channel header shows the new topic without reloading or reopening the channel.
2. Same setup; tab A has the channel open as a member without `ManageChannels`. In tab B, flip `isAgeRestricted` to `true` on that channel, tab A's user having never confirmed → tab A immediately (no reopen) renders the age gate in place of the message list. This is the acceptance criterion directly closing `age-restricted-channels.md`'s recorded gap.
3. Same setup as (2); tab A's user has already confirmed (`ageConfirmedAt` set) → tab A keeps rendering the message list normally, no gate — confirming the refetch does not over-trigger the gate for a confirmed user.
4. Tab A has the channel visible in the sidebar but not open (a different channel is active). In tab B, rename the channel → tab A's sidebar row updates without navigating.
5. Tab A is a member with `ViewChannel` on a channel via role, no explicit override. In tab B, flip that channel's `isPrivate` to `true` (with no override added for tab A's role) → tab A's sidebar drops the channel and, if it was the active channel, `useWorkspaceStore`'s existing fallback selects another channel — within one refetch cycle, no reload.
6. **Failure case**: a member with no `ManageChannels` attempts `PATCH /channels/:id` with any field → `403`, verify via the network tab that no `channel:updated` event is observed on any connected socket (the emit is unreachable after the permission check throws).
7. A socket connected to the server but that has never opened any channel in it (freshly logged in, still on another server) → confirm it does **not** receive `channel:updated` for that server (expected: it also never receives `server:member-updated`/`server:onboarding-updated` today, for the same reason — server-room join is lazy; this is a pre-existing characteristic being verified, not a new bug).

## Deviations

Built 2026-09-25 against the approved spec. Differences from the text above:

1. **`handleOnboardingUpdated` invalidates two keys, not one.** The Changes section describes it as
   invalidating `serverDetail` only; it actually invalidates `serverDetail` **and**
   `serverOnboarding` (`apps/web/src/hooks/useServerModeration.ts:152-158`). No impact: the new
   `handleChannelUpdated` deliberately invalidates `serverDetail` alone, because a channel has no
   separate query key of its own.
2. **Line-number drift.** Current behavior cites `ServerOnboardingUpdated` at
   `packages/shared/src/realtime-events.ts:44`; the real line was 45 before this change.
3. **The cross-reference into `age-restricted-channels.md` was made separately.** The Technical
   approach listed that file among the files touched; it was edited outside the implementation agent's
   file scope, in the same change. Its edge-case table now records that the "stale until reopen" gap is
   closed by this doc.
4. **`packages/shared` must be rebuilt before typechecking**, as Deployment notes predicted — the new
   `RealtimeEvents.ChannelUpdated` export is invisible to `apps/api` until `npm run build:shared` runs.

**Verified** (browser, 2026-09-25, `qa-age-f1` on a channel flipped from another session):
- The age gate rendered in place of a channel that was already open, without reopening or reloading.
- The `18+` badge appeared in the sidebar live.
- A channel rename landed in the sidebar live.
- Confirming age from the gate loaded the message list without a reload.
- No page errors.

**Not verified**: a member losing `ViewChannel` through an `isPrivate` flip (the socket-eviction gap
that stays open as `open-questions.md` #55), and multi-tab behavior.
